# Milestone 02 — Application Logs and Errors

## 1. Objective

Learn how to use application logs and HTTP responses to investigate application behavior, identify failures, distinguish symptoms from confirmed causes, and verify recovery after a controlled failure.

This milestone uses the Expense Tracker application running through Docker Compose. No application code was changed during the experiment.

## 2. Environment and Architecture

The application consists of three Docker Compose services:

- **Frontend:** accessible at `http://localhost:3001/`, with container port 80 mapped to host port 3001.
- **Backend:** accessible at `http://localhost:3000/`, with container port 3000 mapped to host port 3000.
- **MongoDB:** the database dependency, using the named Docker volume `mongo-data`.

The backend exposes two endpoints relevant to this investigation:

- `/health` — reports whether the backend's health handler can respond.
- `/ready` — reports whether the Mongoose connection state indicates that the database is connected.

Docker Compose currently uses `/health` for the backend container health check, not `/ready`.

## 3. Logging Commands Practised

The following commands were used during the investigation.

### Inspect recent backend logs

```bash
docker compose logs --tail=50 backend
```

This displayed the most recent 50 lines of backend logs.

### Follow new log entries

```bash
docker compose logs --follow --tail=0 backend
```

This displayed new log entries as they occurred, allowing requests generated by refreshing the frontend to be correlated with backend activity.

### Restrict logs to a recent time window

```bash
docker compose logs --since=10m backend
```

This helped narrow the investigation to recent application activity.

### Locate logging statements and relevant routes

```bash
grep -RIn --exclude-dir=node_modules --exclude-dir=.git -E 'getTransaction|console\.log|logger\.' app/backend
```

This located logging statements and relevant route/controller references in the backend source.

To inspect health and readiness definitions:

```bash
grep -RIn --exclude-dir=node_modules --exclude-dir=.git -E 'health|ready' app/backend
```

```bash
sed -n '35,65p' app/backend/app.js
```

These commands helped connect observed runtime behavior to the application's implementation.

## 4. Establishing the Baseline

Before introducing a failure, the backend endpoints were tested with:

```bash
curl -i http://localhost:3000/health
curl -i http://localhost:3000/ready
```

Both returned HTTP 200.

The health endpoint returned:

```json
{
  "status": "UP",
  "message": "Expense Tracker Backend is healthy"
}
```

The readiness endpoint returned:

```json
{
  "status": "READY",
  "database": "CONNECTED"
}
```

The frontend was accessible, and sign-in and transaction viewing worked.

This established the normal operating condition against which the controlled failure could be compared.

## 5. Understanding the Existing Logs

The backend logs contained entries such as:

```text
GET /health 200 0.397 ms - 62
POST /api/v1/getTransaction 200 21.784 ms - 549
POST /api/auth/login 200 343.838 ms - 382
```

The request logs provide useful information:

- **HTTP method and path:** which endpoint received a request.
- **Status code:** the HTTP outcome recorded by the logger.
- **Response time:** how long the request took, where available.
- **Response size:** the final value shown by the logging format.

The transaction controller also contained a `console.log` statement that printed the request's user ID, transaction type, frequency, and date range.

For example, the observed log format was equivalent to:

```text
<userId> all 365 null null
```

This corresponds to the controller's extracted values: `userId`, `type`, `frequency`, `startDate`, and `endDate`.

The investigation revealed that the application logs useful request details, but some diagnostic output is unstructured. Logging identifiers and request parameters also requires care because such information can expose sensitive data.

## 6. Controlled Failure Experiment

### 6.1 Prediction

MongoDB was the dependency selected for the controlled failure.

Before stopping it, the expected outcomes were:

- The frontend would remain accessible while its container continued running.
- The backend health endpoint could continue returning HTTP 200 because it does not check database connectivity.
- The readiness endpoint should report HTTP 503 once the backend detected that the database connection was disconnected.
- Database-dependent operations, including sign-in, could fail.

The goal was to test these predictions rather than assume them to be true.

### 6.2 Introduce the failure

MongoDB was stopped without deleting its container or data volume:

```bash
docker compose stop mongodb
```

Docker reported that the MongoDB container had stopped.

### 6.3 Test health and readiness

The following commands were executed while MongoDB was stopped:

```bash
curl -i http://localhost:3000/health
curl -i http://localhost:3000/ready
```

Observed results:

| Endpoint | HTTP status | Response |
|---|---:|---|
| `/health` | 200 | `{"status":"UP","message":"Expense Tracker Backend is healthy"}` |
| `/ready` | 503 | `{"status":"NOT READY","database":"DISCONNECTED"}` |

The experiment confirmed that the backend could still respond to HTTP requests while reporting that it was not ready for database-dependent work.

### 6.4 Observe frontend behavior

The frontend remained accessible at `http://localhost:3001/`.

However, attempting to sign in left the user on the sign-in screen. The application did not display a clear error to the user during this observation.

This was an important distinction: frontend availability did not mean the complete application workflow was functioning.

### 6.5 Inspect backend logs during the failure

The following command was used:

```bash
docker compose logs --since=5m backend
```

The relevant observed entries included:

```text
GET /health 200 0.297 ms - 62
POST /api/v1/getTransaction - - ms - -
POST /api/auth/login 500 30001.979 ms - 59
```

Interpretation:

- Repeated successful `/health` requests showed that the health handler continued to respond.
- The transaction request entries did not contain a final status or response time in the displayed log format.
- The login request returned HTTP 500 after approximately 30 seconds.

The login failure is consistent with a problem accessing the unavailable database. However, the exact internal cause of the delay and failure was not established by the logs alone. Confirming it would require further investigation of the login controller, database operations, and error handling.

## 7. Recovery and Verification

After collecting the failure evidence, MongoDB was restarted:

```bash
docker compose start mongodb
```

The container returned to a running state. Sign-in began working again.

The health and readiness endpoints were then tested again:

```bash
curl -i http://localhost:3000/health
curl -i http://localhost:3000/ready
```

Both returned HTTP 200.

The readiness response was:

```json
{
  "status": "READY",
  "database": "CONNECTED"
}
```

This verified that the backend's reported database connection state had recovered and that the sign-in workflow was functioning again.

The recovery test did not require deleting data, rebuilding images, or modifying application code.

## 8. Findings and Observability Gaps

### Finding 1: Liveness and readiness are different

The health endpoint reports `UP` even when MongoDB is unavailable. This is consistent with its implementation, which returns HTTP 200 without checking the database connection.

The readiness endpoint checks whether Mongoose reports a connected state and returns HTTP 503 when it does not.

Neither signal should be interpreted beyond what it actually tests.

### Finding 2: Docker's current health check has a limitation

The backend's Compose health check calls `/health`, rather than `/ready`.

Consequently, Docker may continue to mark the backend container as healthy while the database connection is unavailable.

This is a configuration gap identified during the experiment, not a change made during this milestone.

### Finding 3: The frontend does not communicate the observed login failure clearly

During the database outage, the frontend remained available but sign-in did not complete. No clear error message was observed on the screen.

This makes the failure less obvious to the user and could complicate support and troubleshooting.

### Finding 4: Logs provide evidence but not necessarily the root cause

The HTTP 500 response and approximately 30-second delay provide useful clues. They do not independently prove which internal operation caused the login failure.

A stronger investigation would correlate the request with detailed application errors and database-driver messages, using a request or correlation ID where practical.

### Finding 5: Some logging is unstructured

The transaction controller prints several request values as a plain console message. Structured logging with appropriate severity levels and contextual fields would make future investigations easier.

Sensitive values should not be logged unnecessarily.

### Finding 6: Error status codes need meaningful semantics

During this experiment, the login request returned HTTP 500. In previously inspected transaction-controller code, a catch block returned HTTP 401 for exceptions. That is worth reviewing because HTTP 401 normally indicates an authentication problem, not every possible server-side exception.

This is a code-review observation, not a change made during this experiment.

## 9. Lessons Learned

1. Start with evidence rather than assumptions.
2. Compare application symptoms, backend logs, health signals, and recent changes.
3. Use timestamps and request details to correlate user actions with backend activity.
4. Distinguish a running process from an application that is ready to serve requests.
5. Interpret each health endpoint according to what it actually tests.
6. Confirm recovery after restoring a failed dependency.
7. Treat logs as evidence, not automatic proof of root cause.
8. Avoid exposing sensitive data through diagnostic output.

## 10. Scope and Limitations

This was a controlled, local development experiment.

- MongoDB was stopped and restarted using Docker Compose.
- No application code was changed.
- No container or data volume was deleted.
- The login failure was observed, but its exact internal root cause was not confirmed.
- The experiment did not evaluate production alerting, centralized log aggregation, or long-term log retention.
- The readiness endpoint checks Mongoose connection state; it does not prove that every database query will succeed.

## 12. Conclusion

The controlled failure demonstrated that an application can remain reachable while an important dependency is unavailable. The frontend remained accessible, the backend health endpoint continued to return HTTP 200, and the readiness endpoint correctly reported HTTP 503 after detecting the disconnected database.

Backend logs recorded a login request that returned HTTP 500 after approximately 30 seconds. Once MongoDB was restored, both health endpoints returned to normal and sign-in worked again.

The main outcome of this milestone is a more evidence-driven approach to troubleshooting: observe the symptoms, inspect logs and health signals, test a hypothesis safely, restore the dependency, and verify recovery before drawing conclusions.
